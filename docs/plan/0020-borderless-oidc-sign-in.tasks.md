AC:
- The system signs users in only through Borderless's OpenID Connect sign-in, as a confidential client from its own server. Applika never asks for, receives or stores a Borderless password.
- Borderless returns every sign-in to `https://applika.dev/api/auth/borderless/callback`, exactly.
- Every sign-in attempt carries a fresh random state and a PKCE S256 challenge. The return is accepted only once, only in the browser that started the attempt, only within ten minutes, and only when its state matches.
- The system accepts a Borderless identity only from an identity token it has verified as signed by Borderless, issued to applika, unexpired, and tied to that one sign-in attempt.
- The system knows a Borderless account by its `sub`, never by its email.
- A sign-in opens the applika account bound to that Borderless account. With none, it binds and opens the account whose email equals the verified Borderless email, ignoring case. With none, it creates a new account. A binding never moves, and the refusals of PRD 0018 R-008 are kept.
- A Borderless account whose email is not verified is refused, with a message asking the user to verify it on Borderless.
- The membership in the identity becomes the badge: BASE gives the BASE badge and PSP the PSP badge, compared ignoring case. FREE, STARTER, any other value or no value gives none. A user holds at most one.
- The system reads the membership at every sign-in, and again whenever it holds no live Borderless access token for the user, by refreshing applika's Borderless grant. It checks at every session refresh, on the web and in every command-line version, and at every request for something that needs the membership. An access token lives about an hour, so Borderless is called about once an hour per active user. The system never uses Borderless's user-info endpoint for this.
- The Borderless refresh token is kept only in the database, always encrypted, and decrypted only when it is used. The system stores the newest one every time it receives one.
- The Borderless access token is never stored in the database. It is kept, encrypted, in the short-term store for no longer than its own lifetime.
- No Borderless token, authorization code, state value or client secret reaches the browser, the command-line tool, a response body or a log.
- When Borderless refuses applika's grant, 30 days after the sign-in or because access was revoked, the system ends every web session of that user and asks them to sign in again on the web.
- In the same case, the user's command-line sessions stay signed in. A command-line request for something that needs the membership is stopped, and the answer tells the user to sign in again on the applika website. The next sign-in restores member access to every session of the user.
- A membership refresh that fails because Borderless is slow, failing or rate-limiting never blocks or ends an applika session. The badges stay as last read and keep counting, and the next check tries again.
- A recorded badge counts as held while the user's Borderless binding is in good standing. It no longer depends on a 7-day token, and no user ever types a password to keep reports.
- Logging out ends only that one session. When it ends the user's last open applika session, the system revokes its Borderless refresh token, best-effort, and leaves the user's Borderless browser session alone.
- A web sign-in uses the user's Borderless browser session when one exists, so signing in again is one click.
- A command-line sign-in always asks the user to sign in on Borderless, even when the browser is already signed in there, and never opens, ends or replaces the browser's own applika session.
- Installed command-line versions 0.1.4 to 1.1.0 keep signing in, refreshing and signing out with no change on their side.
- When a sign-in cannot complete, the user lands on applika's sign-in page with a message, in their language, that says what happened and what to do: the attempt expired or came from another browser, Borderless did not complete it, Borderless is unavailable, the answer could not be verified, the email is unverified, or the account cannot be bound.

- Web sessions ended because Borderless refused the grant appear as ended in the user's Devices list.
