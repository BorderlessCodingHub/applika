## Security
- state: a random UUID (`str(uuid.uuid4())`); browser binding, verifier, nonce: `secrets.token_urlsafe(32)` each (a PKCE verifier needs 43-128 chars); verifier, nonce and redirect target only in Redis; record single use (`GETDEL`), 600 s.
- Cookie `__applika_login` (applika's own): HttpOnly, Secure in PROD, SameSite=Lax (Borderless's top-level GET carries it), Path `{API_PREFIX}/auth/borderless`, Max-Age 600, cleared on every callback answer. A newer attempt overwrites an older one.
- Callback order: cookie hash = record, `state` = record key, `iss` = `BORDERLESS_ISSUER` (RFC 9207), then exchange. Never follows a URL from the query: the target is the one the record stored at the start, re-checked against the allowed targets, `WEB_SIGNIN_URI` or the handoff URL validated at `/auth/cli/*`; a record naming anything else is refused (AUTH-1046), never followed.
- id_token: `jwt.decode(key, algorithms=['EdDSA'], audience=client_id, issuer=issuer, leeway=60, options={'require': ['exp', 'iat', 'iss', 'aud', 'sub']})`; `azp` = client id when present; sign-in `nonce` = record; refreshed `sub` = binding. `none`, HS*, RS* refused by the pinned list.
- Refresh token: Postgres only, Fernet `BORDERLESS_TOKEN_ENCRYPTION_KEY`, never plaintext at rest. LRU `maxsize=1024` per API process, keyed by ciphertext: rotation gives a new ciphertext, old entries are never hit again and age out. Cost: up to 1024 plaintext refresh tokens in each worker's memory; whoever can dump that memory already holds the Fernet key from the environment, so the added exposure is small. Failures are never cached.
- Access token: Redis only, Fernet with the same key (a Redis dump is a database-like exposure), `EX expires_in`, never decrypted, never sent anywhere. id_token never stored.
- Redis: the session check fails closed first (ADR-0019, 503 AUTH-1003); a Redis error after it, in the access store, counts as "missing" and refreshes from Postgres, so the gate fails toward a real Borderless answer, never toward an unchecked membership.
- Secret: `SecretStr`, Basic header per call, never logged. Logs carry status codes and OAuth `error` only; never code, state, tokens, id_token, bodies. caplog tests. Closes 0018 security candidates: password proxy gone, callback `code` not logged; limiter stays fail open (ADR-0015), `/auth/*` bucket covers both routes.

## Contract
- `GET /auth/borderless/login` → 307 `{authorization_endpoint}?response_type=code&client_id=…&redirect_uri=…&scope=openid%20profile%20email%20offline_access&state=…&nonce=…&code_challenge=…&code_challenge_method=S256` + `Set-Cookie: __applika_login` | 307 `WEB_SIGNIN_URI?error=AUTH-1018` | 307 `?error=AUTH-1017` | 429 GEN-1004.
- `GET /auth/borderless/callback?code&state&iss` (or `?error&error_description&state&iss`) → always 307, to the target the attempt's record stored, re-checked; clears `__applika_login`. Web ok: `__access` + `__refresh` of a new `borderless` session (this browser's earlier one ended `replaced`) → `WEB_SIGNIN_URI`. CLI ok: no cookie → loopback `redirect_uri?code&state` or `CLI_MANUAL_REDIRECT_URI?code&state`. Refused → `WEB_SIGNIN_URI?error=<code>` (+ `&cli=1` on CLI flows): AUTH-1046 attempt missing/used/expired/other browser, or a stored target not allowed; AUTH-1047 Borderless `error`; AUTH-1048 `iss`, exchange 4xx, id_token, no refresh token; AUTH-1017; AUTH-1018; AUTH-1005; AUTH-1006/1007/1008; AUTH-1019 CLI login expired; GEN-1005.
- Gone → 404 GEN-1001: `POST /auth/borderless/signin`, `POST /auth/borderless/confirm` (no CLI calls them).
- `GET /auth/cli/authorize`, `GET /auth/cli/login/{id}` → 307 Borderless authorize + `prompt=login` + `__applika_login` (was `WEB_SIGNIN_URI?cli=1` + `__cli_login`); 400/404 unchanged. `/auth/cli/start`, `/auth/cli/exchange`, `/auth/token`, `/auth/revoke`, `/auth/device/*`, `/auth/refresh`, `/auth/logout`, `/users/me/sessions*`: shapes unchanged.
- Grant ended: web session's `GET /auth/refresh` → 401 `{"detail": "Your Borderless sign-in has ended. Sign in again with Borderless", "code": "AUTH-1049"}`, both cookies cleared; the user's other web sessions then 401 AUTH-1002 and refresh 401 AUTH-1015. CLI sessions: `GET /auth/refresh` and `refresh_token` grant answer as today (200, slide).

## Risks
- Rotation lost: Borderless rotates, applika times out or crashes before commit → stored token spent → next refresh `invalid_grant` → web signed out, CLI gated. Bounded by one call per access-token life, 3 s timeout, commit right after the answer.
- Row lock held across one HTTP call (≤ 3 s), as in 0018; a gated request can wait that long once an hour.
- First real run is production: only the prod redirect URI is registered, and the fake can drift from Borderless (claim spelling, `expires_in`, `iss` on error redirects, refresh family rules). Open 1; by-hand walk right after deploy.
- Forward-only after the first sign-in (0018 guard). Deploy window: new image on old schema until step 2; everyone is already signed out.
- Web re-sign-in at most every 30 days for every user (owner's choice); CLI-only users keep their session but lose member features until a sign-in.
- LRU holds up to 1024 plaintext refresh tokens per API process (Security).
- Downgrade label loss: `borderless_revoked` → `revoked` (Devices status identical).
- Key loss → every active user's web sessions end within about an hour of activity.
- Shared computer: applika logout leaves Borderless signed in (owner: Borderless session untouched).
